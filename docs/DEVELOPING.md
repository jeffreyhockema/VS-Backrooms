# Developing Backrooms: Survival Story

How to build the mod, how the code is laid out, the debug commands and the scripts that generate the assets. The design plans and research the mod was built from are in [design/](design/README.md); how it plays now is in the [player guide](GUIDE.md).

## Building and running

You need the .NET 10 SDK and Vintage Story 1.22. The asset generators also need Python 3.10+ with the packages in `tools/requirements.txt` (`pip install -r tools/requirements.txt`).

- **Where the game is:** the build, the VS Code launch config and the generators look for Vintage Story in the `VINTAGE_STORY` environment variable, and otherwise in `%APPDATA%\Vintagestory` (the build and the generators only). Set the variable if the game lives elsewhere. For the build alone you can instead put the path in a git-ignored `Backrooms.csproj.user`: `<Project><PropertyGroup><VintageStory>D:\Games\Vintagestory</VintageStory></PropertyGroup></Project>`.
- **Build:** `dotnet build`. The mod is output to `bin/Debug/Mods/backroomsss/`.
  - Close the game first: a running game locks the mod DLL.
- **Run with the debugger from VS Code:** use the *Vintage Story (client + mod)* launch config (F5). Unlike the build, it has no fallback: it needs the `VINTAGE_STORY` environment variable set (it launches `${env:VINTAGE_STORY}/Vintagestory.exe`).
- **Run without VS Code:** `Vintagestory.exe --addModPath "<repo>/bin/Debug/Mods"`
- **Release zip:** delete `bin/Release` first, then `dotnet build -c Release` writes `bin/backroomsss_<version>.zip`, ready to upload. The zip is the whole `bin/Release/Mods/backroomsss/` folder, and assets are copied only when newer, so an old folder would ship an asset deleted since. A Release build carries no pdb.
- **Version number:** kept the same in `modinfo.json` and `Backrooms.csproj`. The build check (`src/BuildCheckSystem.cs`) compares a fingerprint of the build (the assembly's id and the names of the assets both sides load: blocks, items, entities and recipes are server-only and do not count, though a resource pack adding assets in the `backrooms` domain does), not the version, so a server and client with different copies are warned in chat even when the version matches.

## Keeping saves working

The mod is released, and players have worlds made with it. Every change must leave those worlds loading and playing as before:

- **Codes:** never rename or remove a block, item or entity code, or change a block's variant groups. A world stores blocks and items by code, so a missing code loses them. Add new codes beside the old ones; if something has to go, keep a stub or remap the old code to the new one.
- **Class names:** never rename a registered block, item, block entity, entity or behaviour class that saved chunks refer to.
- **World generation:** a change that would alter what an existing world generates goes behind a new layout version (see *Layout versions* below). Run `layouthash` before and after: the output for every older version must not change.
- **Saved data:** never change what an existing key means; add fields with defaults and read old formats. World save data (`SaveGame.StoreData`): `backrooms-thresholds` (with `-wayback`, and the `-unreadable` backups of both), `backrooms-notes`, `backrooms-notespots`, `backrooms-dens`, `backrooms-wanderers`, `backrooms-end`, `backrooms-endloop`, `backrooms-fun`, `backrooms-hub-entered`, `backrooms-hub-manifest`, `backrooms-l188-windows`, `backrooms-l974-houses`, `backrooms-mapoff` and `backrooms-deathwpoff`. World config: `backroomsLayoutVersion`, `backroomsWorldgenFood` and `backroomsLayoutLevelSize` (written by the mod when the world is made) and the six settings `backroomsMenace`, `backroomsScarcity`, `backroomsMap`, `backroomsLevelSize`, `backroomsThirst` and `backroomsFatigue`. Player attributes under `backrooms:` that carry meaning between sessions (the journal's `visitedLevels`, the Hub's `hubTowerVisited`, `hubKeymasterGift`, `hubKeymasterChoice`, `hubInTower` and `megKeys`, Level 974's `l974*` visit state, `crownGiven`, `nightmareOf`, `killedBy`, `l3999`, the needs' `sickUntil` and `needsNotice`, and the end, fun and run keys; and the needs' watched trees `backrooms-thirst` (`hydration`, `maxhydration`) and `backrooms-fatigue` (`awakeHours`, `caffeineUntil`, `crashHours`, `hinted`), whose absence means full and rested); creature attributes `backrooms:*` are saved with the chunk, and so is a wanderer's site key (`backroomsSite` in its watched `variables` tree, which the dialogue reads as `entity.backroomsSite`). Also block entity attributes, the client's explored-map store and the tutorial's saved step codes (`ModConfig/tutorial-tutorial-backrooms-firststeps.json`, progress by step code).
- **World settings:** keep their codes and option values. A new setting's default must give the old behaviour, because existing worlds don't have it set. The one stated exception is the needs (`backroomsThirst`, `backroomsFatigue`, docs/design/needs/): absent means on, so worlds made before them get thirst and fatigue (the user's decision), and a player joining such a world is told once in chat how to turn either off with `/worldconfig` (read live, so it takes effect at once).
- **The asset domain** stays `backrooms`.

When in doubt, load a world made with the last release and check it.

## Code map

- **`src/Worldgen/WorldLayout.cs`:** deterministic layout with no game dependencies. Contains:
  - the level map;
  - one 32×32 "macro cell" per chunk;
  - shared edges, which are a pure function of the edge so neighbours always agree;
  - per-position temperature.
  - **Ring sizes:** to resize the levels, change `RingWidths` (the average width of each ring in 32-block cells); `Stretch` sets how lopsided they are. Changing them reshapes every existing world, so it would have to go behind a layout version.
  - **Level size** (the world setting `backroomsLevelSize`, 50 to 200 percent): scales every ring by `WorldLayout.RingScale` (`RingWidth`); each level's own plan, and the places past the rings, are untouched. Below 1 no ring is narrower than `MinRingWidths` in any direction; above 1 `RingSqueeze` keeps the outermost ring short of the city's rim, never narrower than at 1. At 1 neither is applied, so a world of the usual size lays out exactly as before at every layout version. Like the layout version it is fixed per world: `BackroomsWorld.RingScale` writes the setting's value (100 in a world made before it) into the world config as `backroomsLayoutLevelSize` the first time it is asked, and only that key is read afterwards. A world made with another size and opened by an older mod version is laid out at 100% from then on, so chunks generated after the downgrade would not line up with the ones already there. The harness takes `RING_SCALE=<x>`.
  - **Layout versions** (`WorldLayout.CurrentVersion`, `Version`): a world keeps the layout version it was made with, recorded in its world config (`backroomsLayoutVersion`, by `BackroomsWorld.LayoutVersion`; worlds made before versions are 1). A fix that would move what an existing world holds goes in behind a new version, never in place, so chunks generated later still match the ones already there. Version 2 rolls Level 37's deep halls apart from their width and Level 5's boiler-bay fittings by row; version 3 gives Level 0 more and fewer picked-over supply boxes. In version 4 a doorway wider than one block has one sign over its middle (EXIT, STAFF ONLY, a store's sign, a Level 3999 unit's neon), drawn in halves over the middle two blocks of an even width (`WorldGenerator.Signs.cs`). Version 5 is the visual-review pass: arrival points picked where you can see the level (`WorldLayout.ArrivalPreference`), Level 4's thinner cable droops, and dressing across many levels. Version 6 makes camp tents and sleeping bags full size (with `WorldLayout.Parts.cs` removing any multi-tile prop that lost a part) and packs Level !'s hallway with set pieces. Version 7 lets the *Backrooms scarcity* setting thin Level 9's gardens and Level 10's crops and berry bushes (`WorldLayout.ThinFood`, from the `FoodScale` the game side passes in); at Normal and Plentiful it lays out as 6. That multiplier is recorded in the world config like the version (`backroomsWorldgenFood`, by `BackroomsWorld.WorldgenFoodScale`: at creation, or on first load for a version 7 world made before it was kept), so changing the setting later still scales drops, dispensers and livestock but never the crops of chunks yet to be generated. Version 8 makes every Level 94 house cream-yellow (some were white) and lets its towns' siren poles stand, placed after the house lots that used to cover them (`PlaceSirenPoles`; `NearestSirenPole` gives the same four corners in every version). Version 9 gives each level its own wall lining the next level's, so neither side sees the other's face, and the Hub its rounded tunnels, among much else. Version 10 (not yet released) joins Level 3's manhole tunnels under every cell, redoes Level 0's arched areas as walls of archways over half walls, breaks Level 8's 9th Road with rockfalls and a cave passage round each, and gives Level 94's fenced yards level plots. Version 11 places tents where they fit, keeps Level 0's party cells out of the inner Lobby, gives every stretch of hotel lobby a front hall, widens Level 3999's rusted-cabinet search to the corners of its reach, and takes a glitch wall only where the alley tile in front is plain floor. It also makes Level 4's windows whole panes, two blocks wide and the window's full height, one state to each pane (`WindowRoll`; the generator's `L4PaneBlock` picks each block's part of the pane). The full list is in the doc comment on `WorldLayout.CurrentVersion`. The harness takes `LAYOUT_VERSION=<n>`; `layouthash` hashes version 1 unless told otherwise.
- **`WorldLayout.Level0.cs` … `.Level11.cs`:** how each level lays out a cell. Level 6.1 is in `.Level6.cs`. Bigger levels have more files: `.Level0.Arches.cs` (Level 0's arch areas, layout 10), `.Level5.Beast.cs`, `.Level8.cs` with `.Level8.Network.cs` (the 9th Road: settlements, braids, breaks and the passages round them; harness `l8roads`) and `.Level8.Nests.cs` (spider nests), `.Level3Runs.cs` (Level 3's pipe and cable runs; `l3runs`) and `.Level11.Rooms.cs`.
  - Shared by the partials: `WorldLayout.Dirs.cs` (the one set of direction helpers: step, turn, opposite), `.Plans.cs` (the lattice plans for Level 2's tunnels, Level 6's trunks and Level 8's roads), `.Reality.cs` (stability and where impossible shortcuts put people down), `.Conduit.cs` (how Level 1's ceiling conduit ends), `.HubVault.g.cs` (generated by `tools/gen_hub_vault.py`: the Hub's rounded tunnels; it is layout, so regenerating it with a changed generator needs a layout version), `Hashing.cs` (the hash every layout decision uses) and `TunnelPaint.cs` (which coat of paint Level 2's steel tunnel doors wear: one rule for the generator and the ways back).
  - Level 11 is a separate region rather than a ring (`InCity`), planned a whole city block at a time (`BlockPlan`).
  - Levels 37 and 94 are regions too, kept as levels 12 and 13 (`WorldLayout.Poolrooms`, `.Motion`; `DisplayNumber` gives the number players see). `.Level37.cs` plans 96-block blocks (`PoolPlan`); `.Level94.cs` works out its hills, roads and towns from coordinates and plans each hilltop (`HillPlan`), each town and the castle. Their floors lie lower than the others' (`WorldGeometry.PoolDrop`, `MotionDrop`).
- **`WorldGenerator.cs`:** turns layout tiles into blocks, with one block rule per level. Levels 6 to 10 are in `WorldGenerator.Deep.cs`, including Level 8's 3D caves and geology and Level 7's sea. `WorldGenerator.Nests.cs` places Level 8's spider nests, `.Stairs.cs` the public stairs and `.Signs.cs` the doorway signs.
  - Level 11 is in `WorldGenerator.City.cs`: façades storey by storey, ground floors, roofs and the subway. Its streets lie `WorldGeometry.CityDrop` blocks lower, so its columns are generated (and lit) over a band of their own.
  - Levels 37 and 94 are in `WorldGenerator.Pool.cs` and `WorldGenerator.Motion.cs`; each is lit over its own band (`WorldGeometry.BandBottomFor`).
- **`WorldLighting.cs`:** computes block light directly with a flood fill over the column and its neighbours' light sources.
  - Vintage Story's engine is far slower with this many lights.
  - Light sources are registered with each chunk, so relighting after block changes still works.
  - What lighting needs of a cell (absorption and light sources) is kept in a small cache: each cell is wanted by nine chunks, and the generator hands over the cell it has just built rather than having it recomputed.
- **Vanilla dressing in the generator:**
  - **`WorldGenerator.Vegetation.cs`:** grass, flowers, ferns, round tree crowns and pond plants for the open-sky levels (9, 10, 11 and 94). Plants are chosen per column from hashes and noise, and the crowns come from the neighbouring trunk tiles.
  - **`WorldGenerator.Caves.cs`:** Level 8's speleothems, glowworms, lichen, fungi, boulders and crystals, and Level 7's seagrass, dead reef and shore litter.
  - **`WorldGenerator.Interior.cs`:** Level 5's boiling sumps.
  - Vanilla plants only sway where they get sunlight (`BlockPlant`), so swaying grass belongs on the open-sky levels. Water plants sway anywhere.
  - Anything placed underneath a plant needs `fertility` above 0.
- **`UndergroundSystem.cs`:** the ground under the levels: `WorldGenerator.FoundationDepth` (8) blocks of concrete under every floor, then vanilla's own terrain, strata, caves and ores from its generators, with the land's sea level put at the floor; no surface features or soil deposits. `/backrooms ground x z` counts what lies under a chunk.
- **`CaveColumn.cs`:** Level 8's cave and ore noise worked out once per column (the few lattice layers a column crosses) instead of once per block, which made Level 8 generate nine times faster.
- **`src/Lights/`:** failing lights.
  - A block entity swaps the panel's look on the client.
  - Only lights near the player are animated.
- **`src/Corpse/`:** the corpse a death leaves (docs/design/corpse.md): `CorpseSystem.cs` catches the stacks the game drops when a player dies (`OnEntityDeath` notes the dying player, `OnEntitySpawned` takes the `EntityItem`s that appear within a second and two blocks of them), puts them in an `EntityCorpse` (`EntityCorpse.cs`: the seraph in the player's copied skin and clothes, or `corpse-bones` for the skeleton; contents behaviour `backrooms-corpsecontents`, a creature-contents dialog) and keeps `CorpseRecord`s in the save (`backrooms-corpses`) for the map markers and the commands. `tools/gen_corpse.py` writes the two entity types and the bones shape. `/backrooms corpse [list|make|simdeath|age [id]|clear]`: `make` puts a corpse with test stacks (a bag among them) at your feet or at the spawn from the console, `simdeath` drops items for a made-up death so the catching is tested without a player, `age` turns the newest body to bones.
- **`src/Salvage/`:** salvage and the behaviour that strips wallpaper and carpet; `Breakdown.cs` (what the building breaks down to, with which tool; a block whose type gives anything but itself is furniture and keeps its drops, unless its code has a class there, and so does anything a player can carry off: the server log's `Breakdown:` line lists both) and `Dismantle.cs` (`BackroomsDismantle`: a piece of wood or cloth furniture broken with a saw comes away whole and is set down turned to face the player; `tools/salvage.py` adds it to the block types listed in its `DISMANTLE`) and `Protection.cs` (the roofs, the tops of the walls between levels and the fixed blocks that never break: a Harmony postfix on the required tool tier, so the client never starts cracking what it cannot break). `/backrooms canbreak x z [y]` lists a column with each block's tier and drops. Assets for rubble from `tools/gen_breakdown.py`.
- **`src/Reality/`:** Reality Stability per area, Reality Shifts (scheduled from the seed and calendar, so nothing needs syncing), and Almond Water's effect. `ZeroSystem` (`src/Reality/ZeroSystem.cs`) handles the hunter sent at zero stability and the blackout at zero, from any cause; the temporal gear is vanilla's, and `BlockBackroomsBed` (`src/Needs/Beds/`) sets the respawn point when you sleep; `HeatSystem` raises the `thirstrate` stat in hot places (`hungerrate` in a world with thirst off).
- **`src/Needs/`:** thirst and fatigue (docs/design/needs/README.md). `NeedsApi.cs` is the surface the other systems call (`Needs.Hydrate`, `CanSleep`, `DirectorMult`, `SetStabilityOffset`, the readers); `NeedsMath.cs` the numbers, with no game dependencies (and the `needstest` checks); `EntityBehaviorThirst` and `EntityBehaviorFatigue` the player behaviours (added by `patches/player-needs.json`; inert outside Backrooms worlds and with their setting off); `NeedsSystem` registers them, sums the named stability offsets (fatigue, thirst, Level 974) into vanilla's `stabilityOffset` once a second, rolls night visits (`MenaceSystem.NightVisit` in `src/Entities/MenaceSystem.NightVisit.cs` puts the hunter down), words "died of thirst" (a Harmony postfix on the server's death message) and tells players of older worlds about the settings.

## The layout harness

`tools/mapgen` is a console program that compiles the game-independent layout code (`WorldLayout*.cs`, `Tiles.cs`, `ThresholdNetwork*.cs`, …) on its own, so layouts can be checked in seconds without starting the game.

- **Build:** `dotnet build tools/mapgen -c Release -o tools/mapgen/out`
- **Run:** `tools/mapgen/out/mapgen <seed> <cells> [mode …]` from any working folder. An unknown mode (or too few arguments for one) is an error; the spawn-site search is the explicit mode `find`. It writes its output files (`tiles.bin`, `overview.bin`, …) there. With no mode it writes `tiles.bin`, the tiles of a square of `<cells>` macro cells round spawn, which `render.py`, `metrics.py` and `reachmap.py` read.
- **Environment:**
  - `LAYOUT_VERSION=<n>` lays out a world made with that layout version (the current one by default; `layouthash` defaults to 1, see below).
  - `FOOD_SCALE=<x>` lays out a world with that scarcity multiplier (0.6 Sparse, 0.33 Scarce; default 1).
  - `RING_SCALE=<x>` lays out a world made with that *Backrooms level size* (0.5 for 50% up to 2 for 200%; default 1). Every mode takes it, `layouthash` included.
  - `SPAWN=<cells>` sets the spawn cell; 16000 is a full-size world.
  - `AT=<mx>,<mz>`, `AT=L<level>` or `AT=S` centres the area on a cell, on a level's first arrival, or on a Snackrooms food court.
  - Mode-specific: `L0HALL=1` also writes `hall.bin` for `hallview.py`; `CELLS=<n>` (`plantmap`: how many boiler halls to draw), `L9BLOCK=x,z` (`l9stairs`: the town block holding that block), `L9LOST=1` (`l9houses`: list the upstairs places not reached), `SIGNGAPS=1` (`runstats`), `DUMP_LEVEL=<n>` (`validate`: dump only that level's failures), `L94PROBE=x,z;...` (`l94fences`), `L8PASS=1` (`l8roads`).
  - `BACKROOMS_NO_FUN_ENTRANCES=1` and `BACKROOMS_NO_188_ENTRANCES=1` leave out the entrances into Level Fun and Level 188, to prove that nothing but the entrances changed the other levels. The layout library never reads the environment: the harness sets these as statics.
- **Checks:**
  - **`layouthash`** hashes every level's layout (levels 0-13 into the `layout hash` line; the far places 14-20 into their own lines and then one `far places hash` line that folds them together, with Level 20 sampled from its first arrival, since the rays rarely reach it: compare that token after touching a far place, because a far-place change leaves `layout hash` alone). Unlike the other modes it hashes layout version 1 unless `LAYOUT_VERSION` is set. Run it before and after any change to world generation: for every layout version but the newest, the output must not change (see *Layout versions* above).
  - `validate` and `validatelevel <n>` check reachability, blocked doorways, elevator pairs and decor facing.
  - `l3runs` tallies Level 3's wall pipes (pieces by length as the player sees them), cable runs, floor cables, gauges and the switchgear cabinets with a pipe coming out of their front, over the area round `AT`; `l3dump x z r` writes `l3dump.json` for `render_l3runs.py l3dump.json out.png`, a map of them from above.
  - `conduitmap [radius]` draws Level 1's ceiling conduit round the first arrival from above and tallies what each run ends against, with the fitting (capped end, junction box) `WorldLayout.ConduitEnds` picks for it.
  - `manholes [maps]` rebuilds the blocks round each Level 3 manhole near the level's first arrival, with the blocktypes' collision boxes, and checks them the way the game moves a 0.6 by 1.85 player: how much floor drops you in, whether the ladder catches you, standing places with the feet in water and a hand on the rungs (where the game moves nobody sideways), the ladder's top, the headroom at its foot and a dry way off it, and the floor you climb out onto. `maps` draws the first two in plan.
  - `tunnels` flood-fills the tunnel (Under 1 and 2, across cell edges) from each Level 3 manhole round the first arrival and prints the distribution of reachable blocks (layout versions 1-9: 9-34, a dead end; from 10: hundreds, a network under the level; counts stop at 5000).
  - `elevsides [level …]` checks what stands beside every elevator along its wall round a level's arrivals (Levels 3, 4, 5, 11, Fun and 3999 by default): wall on both sides, a corner, or an opening right beside the doors. `DUMP=1` adds a plan round the first one (`DUMPAT=x,z` round that place). Level 3999's `3999section` prints the ceilings and headroom of its tall units and a section through each.
  - `links` goes through every threshold kind and back (the `built` column counts doors and elevators built as ways back, `ThresholdNetwork.WayBack.cs`; a few are drawn, with the `/backrooms wayback` line to try them in the game). `wayback [n]` tries a door and an elevator into n arrivals of every level, each the first through, and counts what is built there and what is left a thin spot.
  - Level 9's houses: `l9houses` (two storeys, porches, lamps, signs, upstairs reachable), `l9stairs` (walks every house stairs with the player's box and prints the least headroom on each step), `l9fences` (fences standing side by side, and `fences.txt`, a plan of a town block) and `l9elev` (front and side elevations of each kind of house, `elevations.txt`).
  - Level 94's fences: `l94fences [x z size]` (`tools/mapgen/L94Fences.cs`) tallies the fences in a square of `<cells>` round the mountain (distance from the road, lengths, ends, joins to nothing, one-block gaps, fences on a path or beside a door, pockets they shut in) and writes `l94fences.ppm`, a plan with each fence's joins drawn; `L94PROBE=x,z;...` prints the tiles round given positions instead.
  - Level 11 (`tools/mapgen/L11Rooms.cs`, `L11Checks.cs`): `l11rooms [blocks] [per kind]` finds the enterable ground floors round the city's centre, writes `l11rooms.txt` (a few of each kind in plan, street front up, with their ceiling lights and floor finishes) and prints per kind the props per hundred tiles, props against the plate glass or in front of a doorway, seats facing a wall, the farthest any floor is from a light, floor finishes per building and floor fenced off by furniture; `l11stairs [stations]` walks every subway flight near the centre down and up with the player's box (0.6 wide, 1.85 tall, stepping up 0.6) and prints the highest step and the least headroom, with side views in `l11stairs.txt`; `l11church` draws the churches' fronts and backs with their stained glass and says whether each is symmetric about its door (`l11church.txt`).
  - `dark <0|1> [half-size] [mx mz]` (`tools/mapgen/DarkAreas.cs`): Level 0 or 1's dark stretches. A block-light estimate over the floor (emitting lights, one level a block through open tiles, less the room's height), then the connected stretches under a light of 1, 4 and 8 with their widest extent and, in Level 0, how much of each lies in a blackout zone; and Level 0's mean floor light by zone. Blackout zones are the only large dark areas; Level 1's are a few dead 16-block circuits.
  - `l7 stairs`, `l7 sites`, `l7 trip` and `l7 map <x> <z> <radius> <file>` (`tools/mapgen/L7Stats.cs`): Level 6's stairwells down by depth into the ring, Level 7's entry rooms and sunken rooms by depth, a trip down a stairwell and back up an entry room's stairs through the network, and a tile dump for renderers.
  - `reach` and `path` look for sealed pockets.
  - `notesupply` (`NoteSupply.cs`: ordinary notes per cell by level with every container broken, old and new drop tables, plus loose notes), `archcheck`, `archlist`, `archloot` and `archspots` (`ArchCheck.cs`, `ArchSpots.cs`): Level 0's arched areas (layout version 10): rooms without two walkable bays, arch doors against a wall, orphan piers, unreachable floor, the loot and the boundary papers; every count in `archcheck` should be zero but the totals.
- **Maps:** `overview <R> [step]` writes `overview.bin`, the level of every cell within R cells of spawn, and prints how far out each level starts; `render_overview.py overview.bin out.png` draws it (`docs/levels-overview.png` is `mapgen 12345 360 overview`). `region <level> [angle]`, `citymap`, `regionmap 37|94` and the per-level modes have their own `render_*.py`. `l4plan` (with `AT=L4`) draws Level 4's floor and reflected ceiling (`render_l4plan.py l4plan.bin out.png [scale] [x0 z0 w h]`: troffers, sprinkler heads, diffusers, columns, whiteboards) and prints the heads' spacing and clearances, the columns' spacing and the whiteboard pairs. `l8roads [angle]` maps Level 8's 9th Road over a square of cells in the middle of its ring (or on `AT`) to `l8map.bin` and prints its numbers: how much road, how far the caves lie from it, the gaps between roads, the ways through the level's walls, pieces cut off, arrivals, the time a cell takes, and (in layout version 10) the network's census: settlements, braids, exits and breaks in the road (rubble and the passages round them are drawn pink and green; `L8PASS=1` also walks every passage tile by tile and counts steps over one block); `render_l8roads.py l8map.bin out.png [--scale S] [--crop x,z,w,h]` draws it.
- The other modes, such as `stats`, `loot`, `dens`, `gates` and the far places' own (`runstats`, `funstats`, …), print statistics. They're listed in `tools/mapgen/Program.cs`. `report.sh [seed] [cells] [angle] [levels…]` renders the middle of each level's ring and prints its layout metrics.

## The gate

`python tools/gate.py` runs every automated check the project has, headless, and writes one report. Run it before a merge and before a release. It needs the .NET SDK, Python 3, git bash and Vintage Story (`VINTAGE_STORY`, default `G:\Games\Vintagestory`), and it takes a few tens of minutes (the harness stage is most of it).

- **Stages**, in this order, each timed and ending pass, FAIL or skipped with a one-line reason:
  - `generators`: `gen_guide`, `gen_notes` and `gen_dialogue` with `--check`, and that the checks left the working tree unchanged.
  - `lang`: all lang files (the mod's three, the game-folder ones, the worldconfig ones) parse with `//` lines stripped and have no duplicate key; `en.json` is plain JSON, the two `es` files start with the BOM and `//` lines; each `worldconfig-*.json` has a `worldattribute-` key for the six settings of `worldconfig.json`.
  - `build`: `tools/locked.sh mod gate`, Debug, 0 errors.
  - `boot`: a headless server on a fresh random seed, started with that build; the log must show 0 missing blocks and 0 missing Items, no backrooms error or exception lines, no `[Server Error]`, and no "unknown" or "could not load" recipe, item or block warnings.
  - `mapgen`: builds the layout harness and runs `layouthash` (`mapgen 1 6 layouthash`, `LAYOUT_VERSION=1, 9, 10, 11` and the current version) against `tools/gate.hashes.json`, `validatelevel 0` to `20` and `validate` (seed 12345, 24 cells, `SPAWN=16000`), `deep`, `links` and `shortcuts`.
  - `oldworld`: copies the save named in `tools/gate.config.json` (`oldWorldSave`; default `sunny cave tales.vcdbs`) to a temp data folder as `Saves/default.vcdbs`, boots the build on it, asserts ready with 0 missing and 0 errors and runs `/backrooms ratecheck 1 heartland 20`. The gate refuses any save with "creepy kingdom" in its name (the live one), and only ever reads the source.
  - `harness`: `tools/aitest/run.py --groups all --rerun-failed 1` (every case group and the 60 s dummies smoke), on the port after the base. A failed case is rerun once on the same server.
  - `zip` (only with `--zip` or `--only zip`): removes `bin/Release` and the zip of the current version, runs `tools/locked.sh release gate` (`dotnet build -c Release`), and checks the zip is at `bin/backroomsss_<version>.zip` with no pdb and that `modinfo.json` (repo and in the zip) matches the `<Version>` in `Backrooms.csproj`.
- **Flags:** `--only a,b` and `--skip a,b` (stage names), `--zip`, `--fast` (generators, lang, build, boot and only the harness smoke), `--port-base N` (default 42801; boot uses N, the harness N+1, the old world N+2), `--update-baselines`, `--harness-timeout SECONDS`. `--only boot` alone reuses the last gate build; with no build it skips with the reason.
- **Reports:** `review/gate/<yyyyMMdd-HHmm>.md` and `review/gate/latest.md` (the folder is git-ignored), plus `<stamp>-harness.txt`, the harness's full output. The exit code is non-zero if any stage FAILs.
- **Servers:** the gate stops only servers it started, by PID (`/stop`, then `taskkill /PID .. /T /F`); it never kills by image name, so a running game or another session's server is left alone. A missing old-world save skips that stage (loudly: the reason says so; the exit code stays 0). Use ports outside 42801-42809 for anything else you run at the same time.
- **Baselines** (`tools/gate.hashes.json`, written by the first run): the layout hashes per version, the `validatelevel` and `deep` figures and the `shortcuts` counts. A hash of a past layout version that differs is a FAIL (past versions must stay byte-identical: saves depend on it). The current version's hash differing is only a note while the version is in development; run `--update-baselines` to record it, and do so when a new `LAYOUT_VERSION` is added (its hash is recorded automatically the first time). Baselines are written only by a run with no problems. A `validate`/`deep` figure worse than its baseline is a FAIL; a better one is a note; `--update-baselines` records it. `shortcut` counts that move are a note.
- **A failure means:** `generators`, `lang`: a text or generator output is stale or malformed (run the generator, fix the lang file). `build`: does not compile. `boot`: the content does not load (missing block or item, a broken recipe or a thrown exception at start): the game would show it to every player. `mapgen`: a layout changed (for a past version this breaks existing worlds, so look before updating anything) or a level is no longer walkable or reachable. `oldworld`: an existing world no longer loads cleanly: do not release. `harness`: a behaviour case failed twice or the server log has a backrooms error line. `zip`: the release build is wrong.
- **Flaky-case policy:** the perception cases place straw dummies in a world whose chunks load asynchronously, so a case can fail with "never saw the dummy" or "no spot with a clear line" without anything being wrong. The harness reruns a failed case once on its own; the stage passes if it passes first time or on the rerun, and the report lists the reruns as flaky. A case that fails twice is a failure: do not rerun the whole gate until it goes green, read the case's evidence line in `<stamp>-harness.txt`. A case that needs its rerun often is a case to fix, not to ignore: say so in the tracker.

## Debugging

- **Cheat menu:** press **F7** (rebindable under Controls, "Backrooms: cheat menu") or type `.cheats`. Its buttons send the commands below plus `/time`, `/gm` and `/worldconfig`; they go through the server like typed commands, so you need the controlserver privilege (the menu says so when you lack it), as every `/backrooms` command and `/endloop` below do, and the replies show in chat. A status line on every tab shows your level (display number and id, from this client's layout), where you are from spawn, your game mode and the map and scarcity settings; the menu reopens on the tab you left. Hover over a button for what it does. Code in `src/Cheats/`.
  - **Travel:** go to a level, go beside a feature, the nearest gameplay target (gate, way out, cache, refuge, den, Red Room), **Back** (`/backrooms back`), your wake-up point, where am I.
  - **Player:** game mode, heal, die, a light in hand, stat presets, time out, and the testing and explorer kits.
  - **Creatures:** spawn an encounter (creature, kind, distance), **Perceive** (puts the creature down at the chosen distance, 20 on auto, and reports what it perceives, as `/backrooms perceive` does), **Stop probes**, pause or resume the director, make noise, clear creatures.

Changing scarcity never changes worldgen thinning, which uses the `backroomsWorldgenFood` recorded when the world was made. Clients see the new values when they rejoin.

Usage: `python tools/aitest/run.py --mods <Mods dir>` (`--groups all` is every case and the smoke, `--groups smoke` the smoke alone, `--rerun-failed N` reruns each failed case up to N times on the same server; `tools/gate.py` uses these). The first try only loads the chunks. It reproduces the 0.513.0 empty-harvest bug (client copy 2 s, server copy 5 s: the knife stopped before the server was done).

## Play telemetry

A local event log of the user's own sessions, so a human play-test yields numbers without note-taking. Nothing leaves the machine. Code: `src/Telemetry/TelemetrySystem.cs`; report: `tools/telemetry/report.py`.

- **Where:** one JSON Lines file per server session, `<data folder>/ModData/backroomsss/telemetry/<world>-<yyyyMMdd-HHmm>.jsonl` (on Windows, a single-player game's is `%APPDATA%\VintagestoryData\ModData\backroomsss\telemetry`). The server log says the exact path at start-up. On by default in Backrooms worlds; `/backrooms telemetry` shows the path, `/backrooms telemetry on|off` switches it (the file stays).
- **Each line:** `t` (real UTC time), `h` (in-game total hours), `p` (player; a straw dummy is `strawdummy#id`; `-` for the server), `ev` and the event's fields. No player gets more than 20 events a second (a `throttled` event counts what was dropped); marks and deaths are never dropped.
- **Events:** `session` (state start with world, seed, mod and layout version and the four settings; state end), `join`, `leave`, `level` (from, to, band, class), `band`, `pos` (every 30 s: x, z, level, band, `d` = blocks walked since the last one, game mode), `spawn` (code, kind, band, dist, setpiece; every entity put down by the director or a set piece), `kind` (an owned entity's change of kind, Stalk to Hunt and so on), `contact` (an owned entity first has a line to its target), `damage` (src, type, amount as the health listener saw it, normally after armour, hp left, armour tier), `death` (cause, level, band), `respawn`, `stab` (stability crossing 0.5, 0.3, 0.1 downwards, zero, and back above 0.5), `blackout`, `need` (thirst and rest band changes; sleep start and end), `eat` and `drink` (item), `loot` (a Backrooms cache, crate, supply box and the like opened or broken), `trade` (taken from the trader's audit log line), `note` (key), `cross` (the class-crossing chat line fired) and `mark`.
- **The marker:** F8 ("Backrooms: mark this moment", rebindable) sends `/backrooms mark`; `/backrooms mark <text>` (or `.mark <text>` on the client) adds a note. The `mark` event holds the text, position, level, band, menace value, health, stability, thirst and rest, the menacing entities within 48 blocks (code, kind, distance) and the player's last 60 s of events (`recent`). The reply is "Marked." From the server console it marks the latest straw dummy.
- **Hooks:** `Telemetry.Log(ev, entity, name, value, ...)` and the helpers beside it in `TelemetrySystem.cs` are static and no-ops when the system is off; the spawn, kind, contact, blackout, crossing and note events are one-line calls at their source. Level, band, stability, needs, eating (a stack in hand that shrank while satiety or hydration rose), damage (a listener on the player's health), death, loot and trades are watched from inside the system.
- **Report:** `python tools/telemetry/report.py <file.jsonl|folder> [--out report.md]` prints markdown: per session the minutes by level and band, felt spawn rates per hour by kind and band, time to the first encounter per level, damage by source and armour, deaths, stability lows and blackouts, supplies eaten and drunk per hour, loot per 1000 blocks walked, notes, trades and a timeline of the marks with their context. `--compare docs/design/balance-spec.yaml` is a stub (the spec does not exist yet; the interface is described in `compare()`).
- **Headless test:** start the harness `Server` (tools/aitest/run.py), `/backrooms dummies on`, put a dummy down and `/backrooms encounter hound hunt <x> <z> 12`, then `/backrooms mark test`; the jsonl has the session, spawn, kind and mark events.

## Assets

Textures, 3D models, block definitions and sounds are generated by scripts:

- **Block textures must be a multiple of 8 pixels on both sides**, as every vanilla one is. The block atlas is packed edge to edge and mipmapped down to 8-pixel texels, so a single texture off that grid shifts what is packed after it, and far off those blocks' edges shine as a grid (it once did on Level 0's carpet). `gen_textures.save` and the Level 3999 `save` refuse such a texture; `fit_atlas_grid` scales a picture up by a whole number, and `pad_to_atlas_grid` pads it and gives the face UV that shows only the picture.
- Sounds are written through `tools/oggutil.py`, which leaves a sound file alone when it has not changed.

- `tools/gen_textures.py` (needs Pillow)
- `tools/gen_l0_walls.py`: Level 0's arched areas: the arch header model, and the wall block between an arched area and a papered one, pale on one side and yellow on the other. Run it on its own.
- `tools/gen_shapes.py`: block models such as pipes, fixtures, furniture and machinery, built from boxes
- `tools/gen_blocktypes.py`: block definitions for Levels 3–5 (and Level 2's fittings of layout version 9: `tunnelfitting`, `machinecabinetfeed`, `feedpipe`)
- `tools/fire_fx.py`: candle flames, fire, embers, smoke, steam and `HeatSource` for the props that burn. gen_detail.py and gen_blocktypes.py use it, and the particles are copied from vanilla's candle and firepit.
- `tools/gen_sounds.py` (needs numpy and soundfile): hum, flicker crackle, steam, transformer, rain, jazz, waves, and the squelch, scuttle, breath, whisper and chalk effects
- `tools/gen_loop.py`: the survival loop's assets (torn boxes, emptied crates, the moth hive, wanderers' notes, the pry bar, seed packets, and their text).
- `tools/gen_lore.py`: details added to match the lore more closely (Level 2's doors and clutter, cameras, traffic signs, plaques, ceiling fans, Almond Water seeps).
- `tools/gen_guide.py`: the text of the handbook pages, in a light markup, written into the lang file. Its numbers (uses, recipe amounts, where things are found) come from the block types, recipes and code, so update it when those change. `python tools/gen_guide.py --check` only validates it (it writes nothing), as `gen_notes.py --check` does for the notes.
- `tools/gen_detail.py`: the detail props, wall decorations, signs, doors, elevators and floor variants of Levels 1 and 3–5. Each item is defined once (textures in `detail_textures.py`, helpers in `detail_kit.py`) and gets its texture, model, block definition and English name. It also writes `src/Worldgen/DetailBlocks.g.cs`, the table the world generator uses to find the wall decorations. It calls `tools/gen_deep.py` (textures in `deep_textures.py`) for everything in Levels 6 to 10, including the Snackrooms food and the chalk (and through it `tools/gen_suburbs.py`, Level 9's houses from layout version 9: tall windows, doors that open, the cased garage door, chimney caps, the stairs' balustrade), `tools/gen_city.py` for Level 11, and then `gen_lore.py`, `gen_pool.py`, `gen_motion.py` and `gen_guide.py`.
- `tools/salvage.py`: what breaking each piece of furniture and clutter gives, in one place. It rewrites the drops of the generated block types at the end of gen_detail.py and gen_blocktypes.py.
- `tools/gen_building.py`: the grid recipes for building with the Backrooms (`recipes/grid/build-*.json`: drywall, wallpaper, carpet, ceiling tiles, hotel panelling, concrete, Level 3 masonry, house floors, then the wave-two finishes). It also writes the **built twins**: every recipe output goes through `out(code)`, which gives `built-<code>`, and a twin blocktype of the original (read from its blocktype JSON, only the variants the recipes output, plus what a cut leaves) is written to `blocktypes/built/` with the original's look, sounds and boxes, `drops` of itself, the attribute `backroomsBuilt` (`Breakdown.IsBuilt`: `KindOf` returns `None` for it, so no breakdown class, no protection rule, never kept or replaced by `Apply`) and a `built-*` lang name in all three lang files. A `side`/`facing` original gets `BackroomsHorizontalOrientable` (it picks `facing`, else `side`). Furniture has no twin: it comes away whole only under a saw (`Dismantle.cs`), even when a player set it down. Wave two adds the finishes (houses, roofs, farm, tile, city) and `recipes/barrel/build-asphalt.json` (tar and rubble); its outputs go through the same `out(code)`, so they are twins too. Tar is vanilla's `game:tarportion`, taken from a `backrooms:tar` block with a bucket (`BlockTar.OnBlockInteractStart`, `src/Deep/DeepBlocks.cs`). `BackroomsDismantle` takes an optional `tool` property (default `saw`; `tools/salvage.py` `DISMANTLE_HAMMER` sets `hammer`). Pure Python (needs `json5`), no textures. Keep each shape unique among them and vanilla's, and update the handbook's *Building with the Backrooms* (`tools/gen_guide.py`, with both Spanish files) with it.

- `tools/gen_models.py`: the entities' own animated models, built from the lore's descriptions (Smiler, Hound, Skin-Stealer, Duller, Death Rat, Deathmoths, Clump, the Mangled, The Thing), with their textures painted per face. `tools/rig.py` is the small rigging kit it uses: parts as boxes in model space, an automatic texture atlas, keyframed animations (models face -X, left is +Z).

- `tools/gen_entity_sounds.py`: the entities' sounds and the noises heard down the hall (footsteps, scratching, a murmur of voices, a cough, a mimic's "hello?", knocks, a phone, a Smiler's ringing, a Duller's grab...).

- `tools/texsheet.py <folder or glob>... --out sheet.png [--ref <vanilla texture>...] [--tile]`: a contact sheet of textures at 4x nearest-neighbour with their names, vanilla references in the first row, and with `--tile` each one as a 3x3 repeat to show seams. `--all --out <dir>` does every folder under `assets/backrooms/textures`, each with its vanilla counterparts.
- `tools/check_zfight.py [filters]`: lists z-fighting candidates in the block models: faces of one model in the same plane, facing the same way and overlapping, and faces lying exactly on a neighbouring block's face (an element reaching out of its block). Faces buried inside another element, and undersides on the floor, are left out; what is left still needs judging (a top face against the ceiling never shows).
- `tools/entrender.py shape.json texture.png out.png [anims=walk,idle] [frames=8] [views=side,34,front,back] [scale=70]`: renders an entity model in its animations the way the game composes them, a sheet of frames per animation, to check models and animations without starting the game.
- `tools/lineup.py out.png [yaw=65] [pitch=8] [px=150]`: the mod page's "What lives here" lineup (`docs/screenshots/42-what-lives-here.png`): every creature at its true size (the two giants at half scale), facing the viewer, named underneath. Add a new creature to its `ROSTER`.

- `tools/gen_run.py`, `gen_fun.py`, `gen_end.py`, `gen_hub.py`, `gen_974.py`, `gen_3999.py`, `gen_188.py` (each with its own helper modules): the seven far places' textures, shapes, blocks, items, entities, sounds and names, in their own `<tag>/` folders; run them through `bash tools/locked.sh run python tools/gen_<tag>.py`.
- `tools/gen_plant.py`: Level 5's boiler plant (layout 9). `tools/gen_hub_vault.py`: the Hub's rounded tunnels; it also writes the layout file `src/Worldgen/WorldLayout.HubVault.g.cs` (run through `gen_hub.py`, which paints the texture alternates first). The graphics pass's prop modules (`l1props`, `l4props`, `l5props`, `l11art` and `deepprops`, each with a `_tex` module) are called by the level generators.
- `tools/gen_notes.py`: every wanderer's note (the tracks, writers, classes, gates and marks), written to lang, `config/notes.json`, the folded note and the loose note block, and `docs/design/notes-catalogue.md`; `--check` validates them, including the facts they rely on against the handbook, the README and the player guide (`docs/GUIDE.md`).
- `tools/moddb_preview.py [out-dir] [--mobile]`: renders `docs/moddb-description.html` inside a copy of the live mod database page with headless Chrome, so the page can be checked before it is pasted into the site's editor (source view). The page's images are the JPEG copies in `docs/moddb/img/`, served from GitHub.
- `tools/texlib.py`: shared texture helpers (tileable veined marble, gradients).
- `tools/matlib.py`: the graphics pass's material kit: seamless, seeded surfaces on the 8 px grid (concrete, plaster, paper, painted, brushed and galvanised metal, riveted plate, planks, fabric, carpet, tile, glass, rubber, asphalt, brick and block, the ceiling tile, T-bar and troffer lens) and the operations that finish them (`noise_hv`, `bevel`, `inset`, `ao_border`, `grime`, `rust`, `stain`, `tideline`, `alternates`...). Its docstring gives the shading, tiling and grid rules. New textures start here rather than from `gen_textures.noise_fill`.
- `tools/modelkit.py`: model helpers in `detail_kit.bx`'s element format (bevelled boxes, inset and framed panels, handles, knobs, levers, hinges, push bars, kick plates, grilles, dials and gauges, keypads, legs, rims, and chair, table, cabinet and door), with a texture key per face role so a blocktype can give tops, sides and fronts their own materials.
- `tools/matlib_sheets.py [family...]`: the kit's evidence sheets in `review/b2/` (each surface beside vanilla, plain and tiled, with a seam score; the model helpers through preview_shapes; `rig.shade_fill` against `rig.fill`).
- `tools/iconkit.py`: finishing for the flat 2D item icons: `iconkit.finish(img, seed=...)` gives each one-colour area a soft bevel lit from the top left, rounds the whole silhouette, redraws the outline in a darker shade of the colour inside it and adds a fine grain, keeping the silhouette and every area's mean colour. `ICONS` lists the icons the generators finish when they save them; textures laid on item shapes are not icons. Entity textures get their light from `rig.bake`, which darkens a texel only where another part of the model is close to it (joints, the skin under hair), so large faces get no rim.

**Art rules from the graphics pass** (the reasons are in the lessons of [design/graphics-pass/tracker.md](design/graphics-pass/tracker.md)):

- **Lights stay cubes.** A light block drawn as a JSON shape loses the cube's glow, and the rooms round it go dark. Keep emissive fixtures as cube blocks and put any detail in their textures; to give a cube light different faces, name all six faces in the blocktype instead of `all` (`fluorescentlight.json`).
- **Seamless alternates.** Large surfaces use texture `alternates`, but every version must meet every other at any turn: give the versions one shared broad ground and only their own fine structure, and blend each version's own mottle into the shared field toward its edges with `matlib.turn_safe` for floors that are turned at random. A crack, stain or knot goes in about one version in three (`matlib.alternates`), never in all, or it tiles as a grid. Judge tiling on a mock of the blocktype's real mix of versions and turns, not on a 3x3 repeat of one texture.
- **`randomizeAxes: "xyz"`** on any wall with alternates: the game otherwise picks a block's version from x and z only, so every block up a column shows the same one and a feature stacks into a stripe.
- **The 8 px grid.** Block textures are multiples of 8 px on both sides (see above); patterns on a turned floor are four-fold symmetric about the block centre at the pixel; painted lines that cross block edges stay clean at the seams.
- Hardware (dials, handles, grilles, hinges) is geometry, not paint; a painted copy of a 3D feature beside the real one reads as a fault. Judge surfaces at playing distance in the game (2-6 blocks), not only on texsheets.
- Every item can be set down on the floor (vanilla's ground storage): the generators give their items the behaviour through `detail_kit.ground_storable` (the layout, the boxes and the `groundStorageTransform`), and the hand-written item types in `itemtypes/` and `itemtypes/salvage/` carry the same by hand. A new item needs it too.

**The `review/` folder** at the repo root is git-ignored and holds the graphics pass's working images: `review/baseline/<level>/` (the pass's before shots), `review/<batch>/` (before, after and final runs, `compare-*.jpg` sheets, `sidebyside/` pairs, logs) and `review/compare.html`, the index of every batch's before | after pairs. Nothing in it is needed to build; it exists only on the machine that shot it. Spot lists, side-by-side maps and the decisions that matter are committed under `docs/design/graphics-pass/`.

Large surfaces vary from block to block so they do not tile visibly: floors and carpets are turned at random, ceiling tiles come in several versions (one in a while water-stained) and one stretch of wallpaper in three is older and damp-stained. These use Vintage Story's texture `alternates`.

Re-running them overwrites the files, so remove an asset from its script once you replace it by hand.

Not generated, so edit these by hand: `blocktypes/archheaderstucco.json`, `blocktypes/level1/carcollider.json`, `lang/es-419.json` and `lang/es-es.json`, the seven `recipes/grid/` recipes (clay-from-grit, firewood-from-planks, firewood-from-rottenwood, sticks-from-plank, sticks-from-rottenwood, tinder-from-wallpaper, twine-from-carpet), `textures/gui/transition.png`, and everything under `assets/game/lang/` but `en.json`. Three generators write outside `assets/`: `gen_textures.py` writes `modicon.png` at the repo root, `gen_detail.py` writes `src/Worldgen/DetailBlocks.g.cs`, and `gen_hub.py` (through `gen_hub_vault.py`) writes `src/Worldgen/WorldLayout.HubVault.g.cs`, which is layout code: a changed generator changes the Hub's layout and needs a layout version.

Known churn when re-running: `gen_detail.py` rewrites `blocktypes/detail/exitlintel.json` and `exitlintelpair.json` with a different key order but the same content. Restore them from git.

The playstyle's name and description must live in `assets/game/lang/worldconfig-en.json`, because the world-creation screen reads them before mod assets load.

## Client rig

`tools/clientrig/rig.py` runs the real game client against a dedicated test server and drives it from a scenario file, with nobody at the keyboard. It is the layer that sees what the headless harness cannot: the client's boot log, HUD and chat lines, what a placard looks like, armour really worn.

    VINTAGE_STORY='G:\Games\Vintagestory' bash tools/locked.sh mod rig
    python tools/clientrig/rig.py --mods "$TEMP/backrooms-build/build-rig/Mods" --scenario tools/clientrig/scenarios/boot.yaml [--seed 424242] [--port 42797] [--out review/clientrig/<date>] [--keep-open]

What it does: copies your `clientsettings.json` into its own data dir (`%LOCALAPPDATA%/backrooms-clientrig`, never your saves; sound levels set to 0, view distance 128), puts the shotbot beside the mod (building `tools/shotbot` if need be), starts the server on a fresh world with a stdin pipe, starts the client with `-c localhost:<port>` (a multiplayer client, so losing focus never pauses it), waits until the client is in the world, moves the window off-screen (`SetWindowPos` to x = -4000, no activate) and hands focus to the shell, `/op`s the player (named from the server's join line), runs the steps, and stops the client and server by process id. Output goes to `review/clientrig/<date>/<scenario>/`: `report.md` (steps with timings, the client's "Captured N issues during startup" with the lines after it, server and client error lines, a contact sheet, the chat log), the screenshots, and copies of both logs. The exit code is non-zero when a step fails, the client crashes or the run cannot start.

The off-screen rule: the window steals focus once, at launch. Never minimize it (a minimized window renders nothing and the screenshot comes back empty), and never move it before the world has loaded: a move during the loading screen crashed a client with a shader error. The rig moves it only after the bot's `ready.txt` exists (the level finalized). If a crash log appears or the client exits, the report says CRASH; the game's crash reporter window may then be open on the desktop and has to be closed by hand. Other tools that open console windows should not be started while a batch runs (cosmetic only).

A scenario is a YAML (or JSON) list of one-key steps, run in order; every step passes or fails and the run goes on:

- `bot: <shotbot line>`: any command of `tools/shotbot/ShotBot.cs` (`cmd /backrooms ...`, `tp`, `look`, `ready`, `wait`, `mark`, `slot`...).
- `cmd: /backrooms menace`: a chat line from the client, then waits for the reply (default 15 s; `timeout=N` at the end of the text).
- `server: <console line>`: a line on the server console.
- `face: megplacard`: `/backrooms rig face` finds the nearest block whose code contains the text and the camera turns to it.
- `expect_chat: <text> [timeout=N]`: a chat line since the last step contains the text (tags stripped, case ignored).
- `expect_log: <text>`, `expect_no_log: <text>`: the server or client log has (has not) a line with the text.
- `expect_no_startup_issues:`: no "Captured N issues during startup" in the client log.
- `shot: <name>`, `expect_shot: <name>`: a screenshot (the game's own hotkey), file present and over 20 KB.
- `expect_telemetry: <ev>`: a JSON Lines event in the server data dir; skipped, with a note, when the build has no telemetry.
- `sleep: <ms>`, `note: <text>`.

Server helpers for scenarios are in `src/Cheats/RigCommands.cs`: `/backrooms rig equip <set>` (wears `game:armor-head/body/legs-<set>`), `rig sleep` (puts a hotel bed beside you if none is near and lies down; needs `/backrooms stat rest 0.1` first), `rig face <text>`, `rig walk <blocks>` (moves you along your facing), `rig classdrops <block>` (the scarcity roll at your own position). Scenarios live in `tools/clientrig/scenarios/`: boot, placards, armour, respawn, blackout, scarcity.

## Simulated players

A **walker** is a straw dummy that walks a level like a player would, headless, so a two-hour session per level runs without a client. `src/Entities/MenaceSystem.Walker.cs` (a partial of `MenaceSystem`):

    /backrooms walker start <level> [none|leather|bronze|iron|<set>] [light 0-18, default 7] [minutes, default 120]
    /backrooms walker status
    /backrooms walker stop

What it does: puts a dummy at an arrival spot of the level (`FindArrival`), turns `dummies` on (the director directs it as a player) and plans an A* route with the game's pathfinder (30000 nodes): the nearest gate out of the level and 8 blocks through it, or, in a level with no gate, a loop of four waypoints 150 to 300 blocks apart. It walks it at 0.025 (3.5 blocks a second), runs at 0.05 (7) while a Hunt or Search entity is within 12 blocks, hides (sneak, light off) for 20 s when it sees a stalker within 20 (60 s between hides), and opens the loot blocks (supply boxes, crates, ...) within 6 blocks, which refills its hunger clock. At the end of a route it starts again from a new arrival spot (a lap). Its health is its own 15 points: blows arrive through the dummy's health behaviour, are cut by the armour tier's real items exactly as `/backrooms armourtest` models it (head 20 %, body 50 %, legs 30 %, only blunt, slashing and piercing), and at 0 it dies (`death`), then restarts at an arrival spot (`respawn`). Hunger runs down in 40 minutes; starving costs 0.1 health a second; a fed walker heals 0.1 a second after 8 s unhurt. Leather is `sewn-leather`, bronze `chain-tinbronze`, iron `chain-iron`.

Why it moves the dummy itself: the game ticks entity physics only for entities a connected client is near (`PhysicsManager`: `IsTracked == 0` is skipped), so on a headless server neither the path traverser nor any hunter walks. The walker sets the dummy's position along the A* waypoints; the hunters it meets are as headless as ever (they think and strike when a target is in reach, but do not walk), so **encounter rates are the director's, while chases are not simulated**. Its chunk columns are loaded with `keepLoaded` for each leg and released at the next lap.

Telemetry: under `strawdummy#<id>` with the player events' fields (`level`, `band`, `pos`, `damage` with `raw`, `death`, `respawn`, `loot`, `eat`) plus `walker` events (`start`, `leg`, `lap`, `arrive`, `flee`, `hide`, `end`); the log has `[backrooms] walker ...` lines every minute and a `walker final` line.

    VINTAGE_STORY='G:\Games\Vintagestory' bash tools/locked.sh mod walk
    python tools/aitest/walk.py --mods "$TEMP/backrooms-build/build-walk/Mods" --level 1 [--armour leather] [--light 7] [--minutes 120] [--out review/walk] [--port 42813]

`walk.py` starts a server, runs the walker for the minutes, and writes `<out>/walk-<level>.md` (and the jsonl): minutes by level and band, felt bodies per hour by band, time to first encounter, damage by source before and after armour, deaths, blocks walked, caches opened, the walker's final status line, then the full `tools/telemetry/report.py` report. The harness group `walk` (`run.py --only walk`) has `walker-smoke` (5 minutes in Level 1: placed, 150 blocks or more, no errors) and `walker-struck` (a Hound put on the walker lands blows on it). A walker cannot reproduce a human's choices (see docs/design/testing/tracker.md, "Simulated players").
